# EVision - Soft Computing Based Intelligent EV Charging and Energy Optimization

A simulation-based hybrid **Fuzzy Logic + Genetic Algorithm** approach to
cost-efficient, solar-aware electric-vehicle charging at a shared charging
station, with an interactive Streamlit dashboard.

> **All results are produced by a synthetic-data simulation.** Solar
> generation, electricity tariffs and EV charging sessions are generated by
> configurable mathematical models and a seeded random number generator. They
> are not measurements of a real fleet and are not evidence of real-world
> savings. No trained model, paid API, cloud service, GPU or physical hardware
> is required.

---

## 1. Problem statement

A shared charging station has a **hard grid connection limit** (default 150 kW)
and an on-site **solar array** (default 120 kW peak). Over a 24-hour horizon
discretised into 96 slots of 15 minutes, a fleet of EVs arrives, each with its
own battery capacity, initial SOC, target SOC, charger rating, arrival time and
departure deadline.

Charging every vehicle at full power on arrival is simple but expensive to run:
it creates a demand peak, buys energy during peak-tariff hours and wastes
midday solar. The scheduling problem is to decide **how much power each EV
receives in each slot** so that cost and peak demand fall and solar
self-consumption rises, without violating any physical limit and without
sacrificing departure SOC.

## 2. Objectives

1. Minimise total electricity procurement cost.
2. Reduce peak grid power demand.
3. Maximise utilisation of available solar energy.
4. Deliver as much of each requested energy as possible before departure.
5. Respect station capacity, charger limits, battery capacity and availability.
6. Compare the proposed hybrid against conventional charging strategies.
7. Present everything through an interactive dashboard.

## 3. Soft computing concepts used

### 3.1 Mamdani fuzzy inference system

| Variable | Role | Terms |
| --- | --- | --- |
| urgency | required average power / charger rating | low, medium, high |
| price | normalised time-of-use tariff | low, medium, high |
| solar | normalised on-site solar availability | low, medium, high |
| headroom | remaining shared station capacity | low, medium, high |
| priority (output) | charging priority in [0, 1] | very low ... very high |

Pipeline: fuzzification (triangular / trapezoidal membership functions),
rule firing with min for AND, Mamdani min implication, max aggregation and
**centroid defuzzification**. The rule base holds 18 rules, for example:

- IF urgency is high AND headroom is high THEN priority is very high.
- IF urgency is low AND price is high AND solar is low THEN priority is very low.
- IF solar is high AND urgency is medium THEN priority is high.
- IF headroom is low AND urgency is low THEN priority is very low; a dedicated
  override rule keeps an urgent vehicle at high priority even when capacity is
  critically low.

**Library note.** The engine is a vectorised numpy implementation of the same
Mamdani pipeline rather than a scikit-fuzzy ControlSystemSimulation, because
one inference is needed per (EV, slot) pair. `tests/test_fuzzy.py` rebuilds the
pipeline with scikit-fuzzy primitives and asserts that membership functions and
rule aggregation match **exactly** and that the defuzzified output matches to
within 1e-9. Nothing pretends a library was used where it was not.

### 3.2 Genetic algorithm

- **Chromosome** - real matrix G of shape (n_EVs, n_slots), genes in [0, 1];
  `desired[i,t] = G[i,t] * charger_rating_i`.
- **Decoding** - a raw chromosome is never evaluated directly. `decode_schedule`
  enforces availability, charger rating, remaining battery demand and the shared
  station limit, so every evaluated individual is physically feasible.
- **Selection** tournament, **crossover** uniform gene-wise, **mutation**
  Gaussian with clipping, **elitism** keeps the best individuals, and the
  population is seeded with the two baseline schedules.
- Reproducible seeds, convergence history, best schedule and runtime are all
  recorded and shown in the dashboard.

### 3.3 Hybrid coupling

The fuzzy priority matrix enters the GA in three concrete places:

1. **Population seeding** around the fuzzy priorities instead of uniform noise.
2. **Constraint resolution** - when a slot is over-subscribed, station capacity
   is distributed by weighted water filling with fuzzy priorities as weights.
3. **Guided mutation** - part of the mutated genes is pulled towards the fuzzy
   priority of that (EV, slot) pair.

No neural network or trained ML model is used anywhere in the system.

## 4. Mathematical formulation

Slot duration dt hours, charging efficiency eta:

```
charging_power(t) = sum_i P[i, t]                            [kW]
solar_to_ev(t)    = min(solar(t), charging_power(t))         [kW]
grid_power(t)     = charging_power(t) - solar_to_ev(t) >= 0  [kW]
grid_energy(t)    = grid_power(t) * dt                       [kWh]
cost(t)           = grid_energy(t) * tariff(t)               [Rs]
battery_gain(i,t) = P[i, t] * dt * eta                       [kWh]
```

Hard constraints, enforced by construction and never only penalised:

```
C1  P[i,t] = 0 outside [arrival_i, departure_i)
C2  0 <= P[i,t] <= charger_rating_i
C3  sum_i P[i,t] <= station_capacity
C4  cumulative battery energy_i <= requested_i, so SOC_i <= target_i <= 1
C5  only EVs that still need energy receive power
```

Objective, lower is better, all terms dimensionless:

```
J = w1*cost/cost_ref + w2*peak/peak_ref + w3*unmet/requested
    + w4*delay_norm - w5*solar_used/solar_available
```

`cost_ref` and `peak_ref` come from the uncontrolled baseline of the same
scenario. `w3` is deliberately large (default 8.0) so the optimiser can never
improve J by refusing to charge, and the Algorithm Laboratory ships a
**Deadline first** preset (w3 = 40) for full departure-SOC priority.

**Assumptions (v1):** constant charging efficiency, no vehicle-to-grid
discharge, no battery charging curve, perfect foresight of arrivals,
departures, solar output and tariffs.

## 5. Architecture

```
SC/
  app.py                       Streamlit entry point (UI wiring only)
  config.py                    SimulationConfig - every tunable parameter
  requirements.txt
  .streamlit/config.toml       pinned light theme
  data/synthetic_data.py       solar curve, ToU tariffs, EV session generator
  simulation/
    ev_models.py               Fleet, a struct of numpy arrays
    constraints.py             feasible schedule decoding and validation
    energy_accounting.py       physical energy and cost accounting
  algorithms/
    uncontrolled.py            baseline 1
    rule_based.py              baseline 2, crisp heuristic
    fuzzy_controller.py        Mamdani fuzzy inference system
    genetic_algorithm.py       baseline 3, GA only
    hybrid_optimizer.py        proposed method, fuzzy + GA
  evaluation/
    metrics.py                 metrics and objective, scalar and batched
    comparison.py              run all strategies, build comparison tables
    report_generator.py        Markdown report and CSV frames
  ui/                          one module per dashboard page, plus theme/state
  tests/                       pytest suite
```

Business logic is independent of Streamlit: everything in `algorithms/`,
`simulation/` and `evaluation/` can be imported and run from a plain script.

## 9. Configuring simulations

Everything lives in `config.py` (`SimulationConfig`) and can also be changed
from the dashboard:

| Where | What you can change |
| --- | --- |
| Sidebar | random seed, fleet size, station capacity, solar capacity, charging efficiency, cloud variability |
| Algorithm Laboratory | GA population, generations, crossover and mutation probability, mutation sigma, elitism, tournament size, the five objective weights (with presets), station and solar capacity, peak tariff |

From a script:

```python
from config import DEFAULT_CONFIG
from data.synthetic_data import build_scenario
from evaluation.comparison import run_all, summary_table

cfg = DEFAULT_CONFIG.with_(n_evs=50, seed=11, ga_generations=80)
scenario = build_scenario(cfg)
print(summary_table(run_all(scenario), scenario))
```

## 10. Evaluation metrics

| Metric | Unit | Definition |
| --- | --- | --- |
| Electricity cost | Rs | sum over slots of grid energy times that slot tariff |
| Grid energy imported | kWh | sum over slots of grid power times dt |
| Peak grid demand | kW | maximum grid power over the horizon |
| Average grid demand | kW | mean grid power over the horizon |
| Solar energy to EVs | kWh | solar power actually used for charging, times dt |
| Solar utilisation | % | solar used for charging / solar available, 0 when no solar |
| Energy delivered | kWh | battery-side energy stored, station energy times efficiency |
| Requested energy | kWh | energy needed to move every EV from initial to target SOC |
| Unmet energy | kWh | requested minus delivered, clipped at zero, summed over EVs |
| EVs meeting target | % | share of vehicles whose final SOC reaches the target SOC |
| Average charging delay | h | energy-weighted mean time between plug-in and delivery |
| Constraint violations | count | hard-constraint checks that failed, must be 0 |
| Optimisation runtime | s | wall-clock time of the scheduling call |
| Convergence history | - | best, mean and worst objective per GA generation |

Solar **availability** is never reported as solar **utilisation**. Percentage
comparisons are always relative to the named uncontrolled baseline of the same
scenario, and zero denominators return 0 rather than infinity.

## 11. Dashboard pages

1. **Executive Dashboard** - headline KPIs, saving against uncontrolled
   charging, power overview and the active configuration.
2. **EV Fleet** - searchable, filterable session table with per-vehicle
   outcome, plus arrival and energy distributions and a CSV export.
3. **Energy Simulation** - solar versus demand, tariff versus grid import,
   battery accumulation, station utilisation and a time-slot inspector.
4. **Algorithm Laboratory** - GA parameters, objective weights with presets,
   site settings, a progress indicator and the convergence chart.
5. **Performance Comparison** - all four strategies side by side with absolute
   values, percentage differences and the cost versus deadline trade-off.
6. **Soft Computing Explainability** - membership functions, live inference
   with rule firing strengths, aggregation and defuzzification, fuzzy priority
   heat map, GA convergence, fitness breakdown and the best-found schedule.
7. **Research Report** - a report generated from the actual run, an abstract,
   a report outline and CSV / Markdown downloads.

Navigating between pages never reruns the optimiser; results are cached in the
session until the configuration changes or a new run is requested.

## 13. Limitations and future scope

**Limitations**

- Synthetic inputs only; no measured fleet, irradiance or tariff data.
- Perfect foresight of arrivals, departures, solar output and tariffs.
- Constant charging efficiency, no charging curve, thermal or degradation model.
- No vehicle-to-grid discharge and no reactive power or phase balancing.
- The GA and the hybrid are stochastic heuristics. No global optimality is
  claimed and results vary with the random seed.
- Fuzzy urgency is evaluated once per scenario from the plug-in state rather
  than inside every fitness evaluation, to keep the dashboard interactive.
- The rule-based strategy is a transparent heuristic, not an optimal controller.

**Future scope**

- Stochastic arrivals and rolling-horizon (receding) scheduling.
- Real tariff structures, demand charges and measured irradiance traces.
- Vehicle-to-grid support and battery degradation costs in the objective.
- Multi-station coordination and transformer-level constraints.
- Adaptive or learned fuzzy membership functions, and NSGA-II for an explicit
  Pareto front instead of a weighted sum.

## 14. Academic abstract

This work presents EVision, a simulation platform for intelligent charging of
an electric-vehicle fleet at a shared, solar-equipped charging station. The
scheduling problem is formulated over a 24-hour horizon discretised into
15-minute slots, subject to hard constraints on charger ratings, shared station
capacity, vehicle availability and battery capacity. A Mamdani fuzzy inference
system maps four normalised indicators - deadline urgency, time-of-use price,
on-site solar availability and remaining grid headroom - onto a charging
priority for every vehicle and slot. These priorities seed and steer a genetic
algorithm that evolves a feasible charging schedule against a weighted
objective combining electricity cost, peak grid demand, unmet requested energy,
charging delay and a solar self-consumption reward. The hybrid is compared with
uncontrolled charging, a crisp rule-based heuristic and a plain genetic
algorithm on identical synthetic scenarios. All inputs are generated by
configurable mathematical models with a fixed random seed, so every experiment
is reproducible; no trained model, external data set or physical hardware is
required.

## 16. Deployment

The dashboard is a standard Streamlit app and runs on any host that can serve a
Python web process.

**Render** (blueprint included): `render.yaml` defines a free web service with

```
build:  pip install -r requirements.txt
start:  streamlit run app.py --server.port $PORT --server.address 0.0.0.0 --server.headless true
```

Point Render at this repository (New -> Blueprint) and it reads `render.yaml`.

**Streamlit Community Cloud**: connect the repository, set the main file to
`app.py`; `requirements.txt` is picked up automatically.

**Locally over the network**:

```bash
streamlit run app.py --server.address 0.0.0.0 --server.port 8501
```

The free tiers of hosted platforms sleep when idle and run on a single small
CPU, so the first request after a sleep is slow and large GA budgets take
longer there than on a laptop.
